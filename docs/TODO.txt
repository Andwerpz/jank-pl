(side quest)
Don't make iostream depend on everything that wants to use it to print
- if something wants to use iostream, it also needs to implicitly compile any code that iostream depends on. 
  - this can also have runtime impacts, currently, iostream depends on ed25519, which gives a 0.5 to 1 sec overhead on the
    runtime of any program that uses iostream. 
    - as a sidenote, I should probably look into making ed25519 initialization better.
- we also don't want the stuff using iostream to depend on iostream. 
  - for example, we don't want a freestanding package like container depending on a hosted package like iostream. 
- solutions:
  - make iostream and anything that wants to use it depend on some interface package. They can both adhere to the interface
    and iostream will be able to print out anything that implements the interface or smth. 


(side quest)
Add 'workspaces', collections of related packages, to dylan
- this allows convenient installation of multi-package projects
  - currently installing multi package projects is very annoying since you have to manually install each package
  - you also have to install all the dependencies of a package before installing any package
    - this makes it so that if you have circular dependencies, you have to first install dummy versions of your
      packages before installing the real ones with the dependencies. 
- this allows for better behaviour of packages during development
  - currently, it's most convenient to make all packages refer to the stdlib. 
  - this makes it so that you have to install any changes you made to make them visible to other packages 
  - should be able to just do relative dependencies within the workspace, and these should get transformed 
    into references to the corresponding stdlib packages when installed
  - I suppose references to packages outside of the workspace will have to be references to their corresponding
    stdlib packages, but I think that's fine. 


(side quest)
Add ability for packages to customize their exported files
- should allow packages to choose what files to export, and what paths they are bound to. 
- should look something like:
```
[[export]]
source = "containers/vector"  # path relative to src directory
path = "vector"               # path that packages depending on this one will use
```
- by default, packages should export all their paths exactly like how they're laid out in source
- this will allow packages to have private utility files that aren't exposed to anyone

(side quest)
Make 'assert' have dedicated syntax. 
- assert should be a statement
- should have some syntax like `"assert" , "(" , expression, "," , literal_string , ")" , ";"`
- having a dedicated node for it allows us to nicely include source code location information in the error message
- should also introduce an assert intrinsic
  - the compiler should lower this custom assert call into calling this assert intrinsic
  - this way, the runtime can define how asserts get printed. 
- this would also allow us to have an option to omit all asserts if you want performance
  - could also do this by just having assert as an intrinsic, but it would be much clunkier to use the intrinsic everywhere
- what should the signature of the assert intrinsic be?
  - 'void(i32 cond, u8* msg)'
    - hmm, the builtin assert method would have to concatenate its own line info message with whatever message the user passes in. 
    - I suppose the compiler does have access to whatever string literal was passed in the source code, can just concatenate
      at compile time and emit a new string literal to pass into the intrinsic
- maybe I should just introduce a panic intrinsic? 
  - this way the runtime implementation doesn't have to re-check the condition, it just prints and exits
  - 'void(u8* msg, u64 msg_len)'
    - also pass in the length so panic doesn't have to parse the string for null terminator, it just prints
