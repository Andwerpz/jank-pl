Each file should be compiled seperately instead of compiling them all together. 
- this will improve build times of multi-file projects by just compiling what changed.
  - detecting the things that changed may be relatively problematic though, perhaps it's good practice
    to simply re-compile everything in the case that you modify struct memory layouts. 
  - actually, I think you only need to re-compile files that import the changed file?
    - no, it could be the case that a struct usage is 'hidden'. For example, consider  
``` 
// A.jank
struct A {
    i32 foo;
}

// B.jank
#include "A.jank";
struct B {
    A foo;
}

// C.jank
#include "B.jank";
struct C {
    B foo;
}
```
      Changing the memory layout of A will change the memory layout of C, but it isn't visible to C
      as the implementation details of A are hidden from C by B. 
      For now, I'll just recompile all files that directly or indirectly import a modified file.

- how do we handle templates? 
  - right now templated functions and structs are 'abstract' until they get made 'concrete'.
    it's only when they're made concrete that any code is actually emitted from them. 
  - the main issue now is that two different files when compiled can double-emit the same concrete
    instantiation of a single templated function. 
    Then if I create a function pointer pointing to the concrete templated function from both of the files, 
    they may not point to the same address. 
    - solution here is to let the linker handle de-duplication of concrete templated functions. 
      there's a way to let the linker know that some symbol should only be included once in the final binary. 
  - actually another issue is with templated structs. Suppose that my hashmap uses vector as part of its
    internal implementation details. When a user tries to instantiate the hashmap template, they're also 
    then required to know all about vector in order to actually typecheck the instantiated hashmap
    - bandaid fixes (list them out so I know what to avoid lmao)
      - require the user to also import vector
      - make it so that standard libraries don't import each other too much
    - for an instantiation T<U1, ..., UN>, we want to make visible to the compiler 
      - everything visible to T, so that's all methods defined in T + all imports of T
      - struct interfaces of U1, ..., UN. 
        To make it simple, perhaps should expose everything defined in their respective files
    - the issue with exposing the entire file is you may have defined a helper that was also defined in  
      hashmap, which causes a compilation error. 
      - realistically, this will never happen in the vast majority of cases, but it's pretty annoying when it does
    - a solution to this new issue is placing a priority on methods defined in T + imported by T, so we only
      resort to looking in files defining U1, ..., UN if we cannot resolve from the former. 
      - an issue: suppose we define some universal hash 'template<T> u64 hash(T, x)'
        then the compiler will not bother looking for more specific hash methods defined in U1, ..., UN
        because it can always resolve to the universal hash. 
    - another solution is to provide a way to mark methods as private, so they're only available to other methods
      within the same file. 
      - can probably go further with this, allowing structs, struct methods, struct member variables, and so on
        to be marked private. Of course, all of these come with their own semantics.
      - I think this should definitely be a feature, and it does address the symptoms, but I think the real
        issue is that we don't have a good way to define what external methods to include when compiling 
        a instantiated template. 
    - the issue I have with including the file that contains U1 ... UN is that a 'file' is kinda arbitrary. 
      i think we need some syntactic way to define a group of methods and structs
      - so something like a python module or rust package. Make some artificial compilation unit. 
    - ideally we only provide to hashmap the struct memory layout, and it shouldn't need to go looking around
      for other external functions. 
      - i think we can pretty much do this, it would just require one concession: we would have to pass 
        the hash function into hashmap via function pointer. 
    - one big thing is that we want the generated binary of T<U1, ..., UN> to be consistent regardless of 
      what is visible to the target file. We don't want the behaviour of the template instance to be decided 
      by the context in which it is instantiated. 
    - after much contemplation and discussion, I've settled on just doing the 'include the file that 
      defines U1, ..., UN, as well as everything imported by T and T itself'
      - it's good enough for the vast majority of cases, and also guarantees that the compilation context
        will be the same regardless of context. 
  - one more issue with templated structs: Suppose I have two files, U1.jank, U2.jank, defining structs with 
    the same name "U". Then I instantiate T<U> with the U from both U1.jank and U2.jank. How can the 
    linker tell them apart?
    - if we just mangle the struct names with the filepaths, then the linker should be able to tell that
      they're different. 
    - observe that this shouldn't cause any correctness issues as both U1.jank and U2.jank cannot be 
      imported simultaneously without a duplicate type error

- how do we handle globals? 
  - right now I can order them because I compile all files at once. 
    without that, how would I synchronize global variable initialization?
  - one solution is just to make main dependent on every other file in the project. 
    however that kinda defeats the purpose, because then every time we rebuild, main will be forced to recompile
    which will cause it to parse through all files in the project. 
  - what if instead each global simply exposed a function to call that would just populate the global. 
    and instead of having to parse through every file to discover these functions, we could emit them into some metadata file.
    ofc, we'd have to also emit global node definitions and dependencies into metadata as well
    - how are these initializer functions going to allocate memory for the global?
      right now all globals are allocated sequentially on the stack before main runs. 
      they're addressed during runtime by taking an offset to some dedicated register. 
      the issue is that if we do distributed global initialization, then how is each global going to know its own offset?
    - we can solve this by making the global initializer functions also take in a pointer to the proper memory location on the stack
      then when compiling main the memory locations can be synchronized
    - if we do it this way, then we would still have to recompile main every time we changed any file, 
      it would just be much faster to gather the full list of global functions by looking at the emitted metadata files.

- I probably need to make a build tool that can figure out what files to recompile given the set of changed files. 
  - actually, we can get Make to handle this for us. Given the set of modified files, we want to recompile
    any file that directly or indirectly imports from a modified file. 
    We can emit the dependency graph to Make, and it will figure out the rest.

      if the target doesn't exist -> compile
      if the target is older than any of its dependencies -> compile 
    - Make wants to know for each artifact, what files should it check to see if it needs to rebuild the artifact.
